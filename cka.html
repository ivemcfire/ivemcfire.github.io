Mechanical checklist — the leaks that cost points when the knowledge was fine

Built from a 17-question simulator sit where not one point was lost to a concept. Every loss was mechanical. Run this list, not more theory.

Before you start — there is no setup

alias k=kubectl + completion are PRE-SET in both KodeKloud and the real CKA (PSI) exam. There is nothing to configure. Do not waste clock on a setup block — guides that tell you to are outdated. One check, then work: type k && k get po.
SnippetWhat
--dry-run=client -o yamlgenerate, don't create · k run x --image=nginx --dry-run=client -o yaml > p.yaml
--grace-period=0 --forceinstant delete · k delete pod x --grace-period=0 --force
  • Type these in full. Custom exports ($do, $now) are lost across every SSH hop and new terminal — not worth the habit.
  • The exam is terminal + vim/nano + a Firefox docs window. No VS Code, no IDE. Don't plan around one.

Paste, don't type — kills exact-name fails

Never transcribe a string the grader checks. Select it and paste it. Terminal paste = Ctrl+Shift+V.
  • Paste the nouns: resource names, namespaces, image tags, ports, paths — straight from the question text (it's selectable). No typo = no silent zero.
  • Paste docs YAML skeletons, then paste the question's names into them.
  • Always paste: base64 secrets, tokens, join commands, long flags.
  • Type the verbs: short imperative commands (k get, k create, k describe) — faster typed, and a typo just errors instead of silently failing.
  • Memorize-vs-lookup in one line: verbs typed, nouns pasted.
Docs "copy" buttons and triple-click grab the trailing newline — that newline is Enter, so a pasted command fires before you can read it.
  • Single-line command: type # first, then paste. The whole line is commented — it prints, doesn't run. Read it, up-arrow, strip the #, run. (# beats echo: no $/quote/backtick expansion.)
  • Multi-line / YAML: # only protects the first line. Paste into the editor instead (vim :set paste first).

After you write anything

  • cat the file. Always. A file that exists and a file that is correct are different things.
  • Answer files get bare values — no Name: labels carried over from describe, no JSON quotes or trailing commas from inspect.
  • cat -A on every file answer. It exposes trailing padding spaces that plain cat cannot show. Strip them with :%s/ *$//.
  • Container logs usually go to STDERR (httpd, nginx, most JVM apps). A bare > writes an empty file — use 2>&1 after the >.

After you edit anything

k get rs -n NS                    # new ReplicaSet = the template change landed
k get cm NAME -o yaml | grep X    # ConfigMap edits
  • k edit can silently not save. Verify at the object: new ReplicaSet? generation bumped? Does the READY column show the right container count?
  • get -o yaml is a SNAPSHOT, not a manifest. Before re-applying strip resourceVersion (this one actively breaks — Conflict: object has been modified), uid, creationTimestamp, generation, status:.
  • apply MERGES maps, it does not replace them. Deleting a key from your YAML does not delete it from the cluster. Escape hatch: k replace --force -f, or delete then apply.
  • spec.selector on a Deployment is immutable — no edit path, only delete + recreate. Get it right before the first apply.
  • apply printing unchanged after you edited the file means the edit never reached the object. Same family as generation: 1 after a k edit — the tool told you it did nothing.
  • Duplicate YAML keys do not error — the last one silently wins. Edit the existing block; never append a second selector: / ports:.

Before you diagnose

  • k get <kind> first. A missing object and a selector that matches nothing look identical from the client side.
  • Pending pod with a volume → read the PVC object before re-reading the Deployment.
  • k get po -o wide is the single source of truth for placement. Read the node name, never recall it.

Location

ssh <node> sudo crictl logs <id> > /course/X/file 2>&1   # redirect runs HERE, not there
  • The question names a host → ssh <host> is the first command; hostname proves it landed.
  • Worker hostnames resolve only from their controlplane: base terminal → ssh <cp> → ssh <cp>-node1.
  • Answer-file directories live on the controlplane, not the worker.
  • kubectl does not work from a worker (no admin kubeconfig). SSH only for node-local files / systemctl / crictl.
  • crictl talks to the runtime socket directly → always needs sudo. That's also why it still works when the API server is down.

Docs give STRUCTURE. The cluster gives VALUES. Never type a value you could read off an object.

k get nodes -o wide                   # node names
k get po --show-labels                # labels

  • Never add a field the task didn't ask for — hostnames:, storageClassName: manual, an extra listener. Unrequested values can only cost.

Fatal mistakes — ranked by how often they cost the exam

These are scoring failures, not knowledge failures. Grade every practice question against this list, not just against "did it work".
  1. Over-running one question. Past 15 minutes: flag it and move. The most repeated failure story is running out of time before returning to flagged questions. Budget ~7 min/question, two-pass, bank the cheap ones first.
  2. Wrong namespace / wrong host. A correct answer in the wrong place scores zero. The question names a host → ssh <host> is the FIRST command and hostname proves it landed; explicit -n on every graded command. (Cluster switching is the rarer case — k config use-context <name> when a question actually names a context.)
  3. Not verifying before moving on. Exercise the object, don't re-read it. Endpoints populated ≠ something listening. auth can-i --as matches a username string, not an existing ServiceAccount.
  4. Static pod edited with kubectl. It is a FILE in /etc/kubernetes/manifests/ on the control plane. Never k delete, never k edit.
  5. ConfigMap changed without a restart. env / envFrom / subPath mounts → k rollout restart deploy <name> -n <ns>. A plain volume mount self-syncs.
  6. -f reflex on a Kustomize task. A kustomization directory needs -k.
  7. No backup before editing something critical. k get X -o yaml > backup.yaml — five seconds.

Two personal additions

  • When a question names a host, do the whole question from that host — diagnosis, fix, and proof. Verifying from somewhere else is how a working fix gets graded as a miss.
  • Strip what the task didn't ask for. Docs examples carry extra fields; they come along for the ride and can only cost.

Workloads — create / inspect / modify

HPA + ResourceQuota

The hard version of this task: an HPA that scales to 3 pods, where the memory requests must be cut so 3 pods fit under a quota. With a quota of 1100Mi and pods requesting 600Mi, three of them need 350Mi each.

k autoscale deploy web -n NS --min 1 --max 3 --cpu-percent 50
k describe quota -n NS                          # Used vs Hard — the discovery step
k set resources deploy web -n NS --requests=memory=350Mi

Budget ÷ replicas, round down, leave headroom: 1100 ÷ 3 = 366 → use 350. Write YAML only if the task names behavior, stabilization windows, or a non-CPU metric.

  • A quota counts requests, not limits. The scheduler reads requests too; limits only bite at runtime (OOMKill).
  • A quota on requests.memory makes a memory request mandatory — a Pod without one is rejected.
  • Over quota surfaces on the ReplicaSet, not the Pod: k describe rs -n NS → exceeded quota. There's no Pending Pod to inspect.
  • cpu: <unknown>/50% = no metrics-server. The object is still correct and still grades.
  • The HPA needs a CPU request — utilization is a percentage of the request. No request, no denominator, no scaling.
  • HPA changes the replica count; VPA changes per-pod requests and is not on the exam.

HPA behavior — stabilization windows and scaling policies

Needed the moment a task names a stabilization window, a scale-up/down rate, or a non-CPU metric. k autoscale submits autoscaling/v1, but the API serves v2 — so generate first, then edit, and the metrics: block is written for you. Do not hand-author the whole object.

k autoscale deploy orders -n api --min 3 --max 12 --cpu-percent 70
k edit hpa orders -n api                        # opens as v2, metrics: already filled
# add under spec: — behavior is a sibling of metrics/minReplicas
  behavior:
    scaleDown:
      stabilizationWindowSeconds: 120           # wait this long before scaling down
    scaleUp:
      policies:
      - type: Pods                              # or Percent
        value: 2
        periodSeconds: 60                       # at most 2 pods per 60s
  • scaleDown / scaleUp are maps, not lists — no -. policies under them is a list. k explain hpa.spec.behavior.scaleDown settles it: <Object> = no dash, <[]Object> = dash.
  • stabilizationWindowSeconds is a direct key, not a policy field. periodSeconds inside a policy is a different thing — the rate limit, not the wait.
  • Declaring policies replaces the defaults for that direction; the other direction keeps its defaults.
  • Defaults if you write nothing: scale-down window 300s, scale-up window 0s.
  • autoscaling/v1 has no behavior field and uses targetCPUUtilizationPercentage; v2 uses the metrics: list. Mixing them is the usual failure.
  • Read it back with k get hpa NAME -n NS -o yaml | grep -A18 behavior: — a short -A cuts off stabilizationWindowSeconds, which sorts last.

Rollout

k rollout status deployment/NAME      # wait until complete
k rollout history deployment/NAME     # list revisions
k rollout undo deployment/NAME        # revert to previous
k rollout undo deployment/NAME --to-revision=2
k rollout restart deployment/NAME     # force pod re-creation
k annotate deploy NAME kubernetes.io/change-cause="image 1.27"
  • --record is gone. The key must be exactly kubernetes.io/change-cause — any other annotation never appears in rollout history, which will simply show <none>.
  • Annotate the revision you want labelled before moving off it: rollout undo replays the old revision including its change-cause.
  • rollout undo does not reuse the old number — it replays that revision as a new one, and the original number disappears from the history.

Gotchas

  • run = pod, no resource noun (docker run legacy). k run pod catalog → pod NAMED pod, catalog becomes the container command → CrashLoop. create needs the noun; run never does.

Headless Service — what it is and why the StatefulSet needs one

A headless Service is a Service with clusterIP: None. It gets no virtual IP and does no load-balancing. Its only job is DNS.

  • Per-pod name pattern: <pod>.<service>.<namespace>.svc.cluster.local. Inside the same namespace cache-0.cache-svc is enough.
  • serviceName must match the Service's name exactly. Mismatch = pods run fine, ordinals look right, and no per-pod DNS name ever resolves — a silent failure with no error anywhere.
  • The Service's selector must match the StatefulSet's pod labels, same as any Service. Wrong selector = empty endpoints.
  • A headless Service still works if it exists before the pods — create it first, or the first pods start with no DNS until it appears.
  • Headless is not StatefulSet-only: any Service can set clusterIP: None when the client should see all backends (peer discovery, gRPC client-side LB).

Placing a Pod on a node — three mechanisms, pick ONE

These are alternatives, not a stack. A task needs exactly one of them. Writing two is how you end up with a Pod that is Pending for a reason you did not author — nodeSelector and nodeAffinity together must both match (AND, not fallback), and nodeName overrides the scheduler entirely so the other two are never even read.
spec:                                    # ══ pick exactly ONE of ① ② ③ ══

  # ① nodeSelector — exact label match. Simplest thing that works.
  nodeSelector:
    disktype: ssd
  #   ...or pin to ONE NAMED NODE, still scheduled properly — the most-asked form:
  nodeSelector:
    kubernetes.io/hostname: cluster1-node01

  # ② nodeName — skip the scheduler, hand the Pod to one node.
  nodeName: cluster1-node01

  # ③ affinity — everything nodeSelector cannot express (OR, NotIn, Exists, soft).
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:      # HARD — no match = Pending
        nodeSelectorTerms:
        - matchExpressions:
          - { key: disktype, operator: In, values: [ssd, nvme] }
          # pin to a named node the affinity way:
          # - { key: kubernetes.io/hostname, operator: In, values: [cluster1-node01] }
      preferredDuringSchedulingIgnoredDuringExecution:     # SOFT — no match = schedules anyway
      - weight: 1                                          # 1-100; a list, note the dash
        preference:
          matchExpressions:
          - { key: zone, operator: In, values: [eu-west] }

  • A Pending Pod with no events at all is the nodeName signature — a typo’d or nonexistent node name, and no scheduler ever looked at it. Every other placement failure produces FailedScheduling.
  • Affinity needs all three levels: nodeAffinity: → requiredDuringSchedulingIgnoredDuringExecution: → nodeSelectorTerms:. Skipping the middle one is rejected.
  • nodeSelectorTerms is a list and its entries OR together; matchExpressions inside one term AND together. Two terms = “either”; two expressions in one term = “both”.
  • The preferred form is a list of weighted preferences (- weight: + preference:), a different shape from the required form. Mixing the two shapes is the usual rejection.

Pod affinity / anti-affinity — placement relative to other Pods

  affinity:
    podAntiAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
      - labelSelector:
          matchLabels:
            app: web
        topologyKey: kubernetes.io/hostname     # "same node" = the domain
  • topologyKey defines what “together” means. kubernetes.io/hostname = same node; topology.kubernetes.io/zone = same zone.
  • podAffinity attracts (co-locate), podAntiAffinity repels (spread). Both are lists — note the dash, unlike nodeAffinity’s required form.

Gotchas

  • Pin to a node by NAME → key kubernetes.io/hostname. node-role.kubernetes.io/* labels have EMPTY values — they can never match a node name.
  • Read identifiers off the object, never from memory: k get nodes for names, k get node cluster1-node01 --show-labels for keys.
  • Affinity needs all three levels: nodeAffinity: → requiredDuringSchedulingIgnoredDuringExecution: → nodeSelectorTerms:. Skipping the middle one = rejected.
  • Affinity is a POD property — in a Deployment it goes at template.spec.affinity (6sp, sibling of containers:).
  • operator: Exists → NO value: line (matches any value); operator: Equal → value: required. Both together = the Pod is rejected: value must be empty when operator is Exists.
  • Toleration value is string-exact — a typo (mortain ≠ mortein) leaves the pod Pending: the "but I added a toleration!" trap. Paste the noun.
  • No matching node (nodeSelector / required affinity) = pod Pending forever.
  • Pending diagnosis: k describe po web -n apps → Events → "untolerated taint" / "didn't match node selector".

The model (the whole game)

SlotMeans
spec.podSelector (top)WHO you protect — the destination (app=db). {} = all pods in ns.

Read the task — "traffic TO db FROM web" — straight into the two slots. The two selectors are different pods. A wrong key on the top selector matches nothing → the policy applies to no pod → silent allow-all. policyTypes listed with no matching rules = deny-all that direction (Egress alone cuts DNS).

Allow ingress pod → pod (the 90% case)

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-web-to-db
  namespace: prod
spec:
  podSelector:
    matchLabels: { app: db }       # protected (TO)
  policyTypes: [Ingress]
  ingress:
  - from:
    - podSelector:
        matchLabels: { app: web }  # allowed (FROM)
    ports:                         # optional; omit = all ports
    - { protocol: TCP, port: 80 }

Variants — swap the from block

  • From a whole namespace: - namespaceSelector: {matchLabels: {kubernetes.io/metadata.name: dev}}
  • ns AND pod (a specific pod in dev): both selectors in ONE - item — namespaceSelector dashed, podSelector its no-dash sibling.
  • ns OR pod: two separate - items.
  • Deny-all ingress: podSelector: {} + policyTypes: [Ingress] + no ingress rules.
  • Egress: policyTypes: [Egress] + egress: [{to: [...], ports: [...]}].

Egress — the DNS trap

Any egress policy selecting a Pod kills its DNS unless you re-allow port 53. The symptom misleads: name resolution dies, so every destination looks blocked — including the one you just permitted.

  egress:
  - to:                                  # the destination you want
    - podSelector:
        matchLabels:
          app: db
    ports:
    - protocol: TCP
      port: 80
  - to:                                  # + DNS, or nothing resolves
    - namespaceSelector:
        matchLabels:
          kubernetes.io/metadata.name: kube-system
    ports:
    - protocol: UDP
      port: 53
    - protocol: TCP
      port: 53
  • Shorter DNS allow: omit to: and give only ports: — that port, any destination.
  • Probe by IP as well as by name. Name fails while IP works = the DNS symptom.
  • kubernetes.io/metadata.name is not on the NetworkPolicy docs page — its examples use hand-made labels. Read it off k get ns --show-labels; its docs home is Well-Known Labels, Annotations and Taints.

Verify both directions (always) — busybox:1.28

k get po -n prod -o wide -l app=db                # the destination IP

# ALLOWED: prober carries the trusted label -> page comes back
k run t -n prod --labels app=web --image=busybox:1.28 --rm -it --restart=Never -- wget -qO- -T 5 10.244.1.7:80

# BLOCKED: no label -> must fail (this is the half that proves the policy)
k run t -n prod --image=busybox:1.28 --rm -it --restart=Never -- wget -qO- -T 5 10.244.1.7:80

# cross-ns case: run the allowed probe IN the allowed namespace
k run t -n dev --labels app=web --image=busybox:1.28 --rm -it --restart=Never -- wget -qO- -T 5 10.244.1.7:80

The policy trusts the label, not the pod name or image — the allowed prober just needs the right label, in the right namespace. It also needs a working tool: nginx has no wget, so use busybox pinned to :1.28 (latest returns a false connection refused).

A probe run seconds after k apply can pass through. The CNI needs a moment to program the dataplane — re-probe before believing a result on a policy you just created.

Gotchas

  • Separate - = OR; two selectors in one - = AND. Trips everyone.
  • Cross-ns allow test: the prober must ALSO run in the allowed namespace — right label + wrong ns = deny path. Check pod dev/t in the probe output.
  • Always prove the deny — an OR-bug policy and a dead CNI look IDENTICAL from the allowed side (both succeed). Only the blocked probe distinguishes them.
  • Source ns must carry a label to match — built-in kubernetes.io/metadata.name.
  • CNI without policy support (bare flannel) = policy silently no-ops. Test it: apply a deny-all and probe.
  • Deny shows as timeout OR connection refused depending on the CNI (drop vs reject). Don't read allow/deny off the error string — judge by the controlled comparison: labeled pod gets in, unlabeled is blocked.
  • Running ≠ serving: a -- sleep override leaves the pod Running but its port closed (→ refused). Verify the target with a probe, not the status phase.
  • Wrong namespace = 0 points. Set it before anything else.

Cluster Ops — etcd, node maintenance, kubeadm upgrade

Control-plane cert expiry — apiserver down / kubectl x509

Read the error to find which cert died: kubectl failing x509 = the client cert in admin.conf / ~/.kube/config; apiserver down = the server certs in /etc/kubernetes/pki/. Usually both, since kubeadm certs expire together at one year.

ssh <controlplane>
date                                   # clock skew reads as "not yet valid" — renewal won't fix that
kubeadm certs check-expiration         # whole picture, incl. the kubeconfigs
kubeadm certs renew all                # pki/*.crt AND admin/controller-manager/scheduler.conf

Renewal alone changes nothing for the running components. Restart the static pods by moving the manifests out and back:

mkdir -p /tmp/mf
mv /etc/kubernetes/manifests/*.yaml /tmp/mf/
sleep 25
mv /tmp/mf/*.yaml /etc/kubernetes/manifests/
# then refresh the client config, or kubectl keeps failing against a healthy cluster
cp /etc/kubernetes/admin.conf $HOME/.kube/config
chown $(id -u):$(id -g) $HOME/.kube/config

Verify on the wire, not from the files — check-expiration reads what is on disk, not what is being served:

openssl s_client -connect localhost:6443 </dev/null 2>/dev/null | openssl x509 -noout -dates
grep client-certificate-data $HOME/.kube/config | awk '{print $2}' | base64 -d | openssl x509 -noout -dates
  • The manifest path is /etc/kubernetes/manifests/; confirm on any cluster with grep staticPodPath /var/lib/kubelet/config.yaml.
  • kube-apiserver reloads its serving cert without restarting — so RESTARTS 0 is not proof the renewal failed. controller-manager and scheduler do NOT reload; they read their kubeconfigs once at startup, which is why the restart is still required.
  • kubeadm certs renew does not touch kubelet’s auto-rotated cert in /var/lib/kubelet/pki/.
  • kubeadm upgrade renews certs as a side effect — why upgraded clusters never hit this.
  • kubeadm lives on the control-plane node only — command not found on the bastion means you skipped the ssh.

etcd — the cert rule (the whole confusion)

snapshot save talks to the live server → needs endpoint + 3 certs (mTLS). snapshot status / restore just read a file → no certs, only --data-dir. That's why only save has the flag wall.

etcd backup (run ON the controlplane)

ETCDCTL_API=3 etcdctl snapshot save /opt/etcd-backup.db \
  --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key

# verify (no certs needed)
etcdutl snapshot status /opt/etcd-backup.db --write-out=table

etcd restore + repoint

etcdutl snapshot restore /opt/etcd-backup.db --data-dir=/var/lib/etcd-from-backup

Then edit /etc/kubernetes/manifests/etcd.yaml → under volumes:, the etcd-data volume → change one line, its hostPath.path:

  volumes:
  - hostPath:
      path: /var/lib/etcd-from-backup    # CHANGE this line only
    name: etcd-data

kubelet auto-restarts etcd on save. kubectl hangs ~30-60s (apiserver restarts too) → wait → k get pods -n kube-system.

etcd gotchas

  • Change hostPath.path (host dir), NOT --data-dir/mountPath (both in-container /var/lib/etcd).
  • Restore success = final log line restored snapshot — no literal "success" word.
  • etcdctl version must show API 3.x (snapshot is v3-only); export ETCDCTL_API=3 if old.
  • Restore into a NEW dir, never over live /var/lib/etcd.
  • etcdctl = client to server (certs); etcdutl = offline file tool (no certs).
  • etcdutl often not installed (not in the etcd-client pkg) → fall back to etcdctl snapshot status/restore (deprecation warning, still works). Lab missing etcdctl too (KodeKloud quirk) → apt-get install -y etcd-client; the real CKA has it pre-installed.

A tiny file in a PKI directory is a SYMLINK until proven otherwise

ls -l <dir>           # a symlink's size = length of its TARGET PATH, never content
readlink -f <link>    # where it actually points
cat <link>            # dangling -> "No such file or directory"
grep -c BEGIN f.pem   # cert+key pem has TWO BEGIN blocks; one = half a pair

Node prerequisites & CNI — the Linux side of the exam

Recognition rule: a list of kernel modules, sysctls, or a package install on a NODE is Kubernetes work. It does not look like YAML, which is exactly why it gets missed. Both node-side questions on the 08-15 paper were nearly lost to not recognising the task, not to missing commands.

The five settings — container runtime prerequisites

Two kernel modules and three sysctls. Each one needs both halves: a file so it survives reboot, and an activation so it applies now.

cat <<EOF | sudo tee /etc/modules-load.d/k8s.conf
overlay
br_netfilter
EOF
sudo modprobe overlay
sudo modprobe br_netfilter

cat <<EOF | sudo tee /etc/sysctl.d/k8s.conf
net.bridge.bridge-nf-call-iptables  = 1
net.bridge.bridge-nf-call-ip6tables = 1
net.ipv4.ip_forward                 = 1
EOF
sudo sysctl --system

Order is the trap. net.bridge.bridge-nf-call-iptables and -ip6tables do not exist as sysctl keys until br_netfilter is loaded — write the sysctls first and sysctl --system errors on unknown keys. Modules → sysctls → verify, never any other order.

lsmod | grep -E 'overlay|br_netfilter'
sysctl net.ipv4.ip_forward net.bridge.bridge-nf-call-iptables net.bridge.bridge-nf-call-ip6tables
  • Verify from the kernel, not the file. A correct file with an unloaded module scores zero and looks right.
  • /etc/modules-load.d/ = load at boot (systemd-modules-load.service reads every *.conf, one module per line). modprobe = load now. You need both.
  • sysctl --system applies every *.conf from all sysctl dirs; sysctl -p <file> does just one. Either scores.
  • The filename k8s.conf is convention, not requirement — the grader reads kernel state.
  • dpkg -i does not resolve dependencies. If it errors: apt-get install -f, or apt install ./pkg.deb.

The CIDR trap

Diagnosing — and why Ready lies

k get nodes                              # NotReady
journalctl -u kubelet -n 50 --no-pager | grep -i cni
# NetworkPluginNotReady · cni plugin not initialized · network plugin returns error

k run t --image=nginx && k get pod t -o wide    # IP column populated = actually working
  • A node flips Ready as soon as a conflist exists in /etc/cni/net.d/ — even if nothing programs the network. Only a pod with an IP proves it.
  • coredns Pending or ContainerCreating is the first workload to need the pod network. NotReady nodes + coredns not running ⇒ CNI, before you look anywhere else.
  • Lowest-numbered file in /etc/cni/net.d/ wins. A stale 10-old.conflist beats your 20-new.conflist — move it out, don't just add yours.
  • Calico’s 10-calico.conflist is written by the calico-node DaemonSet. If you are hand-editing it, you are on the wrong layer.
  • Init:CreateContainerError is always a container spec problem — mount, path, device, capability. Never networking, never the image. describe names it outright.
  • Debian: containernetworking-plugins installs to /usr/lib/cni but kubelet reads /opt/cni/bin. sudo ln -s /usr/lib/cni/* /opt/cni/bin/.

The chain (4 nouns, always this order)

SA → Role → RoleBinding → verify = who → what they can do → glue → prove. Memorize the shape; look up the flags with --help.

Namespaced (Role + RoleBinding) — -n on ALL THREE creates

k create sa auditor -n finance
k create role pod-reader -n finance --verb=get,list,watch --resource=pods
k create rolebinding auditor-bind -n finance --role=pod-reader --serviceaccount=finance:auditor

Two resources with DIFFERENT verb sets = two rules

One k create role applies every verb to every resource. When the task says read pods, and also create deployments, that is two rules — make the role, then add the second rule in the editor:

k create role app-manager -n finance --verb=get,list,watch --resource=pods
k edit role app-manager -n finance
rules:
- apiGroups: [""]                 # "" = core group (pods, services, configmaps)
  resources: ["pods"]
  verbs: ["get","list","watch"]
- apiGroups: ["apps"]             # deployments live in apps
  resources: ["deployments"]
  verbs: ["create"]
  • Same verbs for several resources? One rule, comma list: --resource=pods,services.
  • Restrict to named objects: --resource-name=web --resource-name=api (no wildcard, and it blocks list).
  • Forgot which apiGroup a kind is in: k api-resources | grep -i deployment → the APIVERSION column.

Verify (impersonate the SA — test an ALLOWED and a DENIED verb)

k auth can-i list   pods --as=system:serviceaccount:finance:auditor -n finance   # yes
k auth can-i delete pods --as=system:serviceaccount:finance:auditor -n finance   # no
k describe rolebinding auditor-bind -n finance    # Role: + Subjects: — proves the glue

A yes alone proves nothing. A too-broad role also answers yes; the denied probe is what shows the scope is right.

Cluster-wide (ClusterRole + ClusterRoleBinding) — NO -n

k create clusterrole node-reader --verb=get,list,watch --resource=nodes
k create clusterrolebinding node-read --clusterrole=node-reader --serviceaccount=finance:auditor
k auth can-i list nodes --as=system:serviceaccount:finance:auditor

ClusterRole + ClusterRoleBindingcluster-wide, plus cluster-scoped kinds (nodes, PVs)
ClusterRole + RoleBindingthe ClusterRole's rules, limited to the binding's namespace — the reuse trick
Role + ClusterRoleBindinginvalid — does not exist

The two SA syntaxes (the slip)

WhereFormat
--serviceaccount=finance:auditor (ns:name)

Gotchas

  • Bind the role you made, not built-in admin (admin = broad, breaks least-privilege).
  • --serviceaccount= with no namespace → defaults to default:auditor → binds nothing.
  • All three namespaced creates need -n — silent zero otherwise.
  • Multiple verbs/resources = comma list, no spaces: --verb=get,list,watch.
  • Bind to a user/group instead of an SA: --user=jane / --group=devs. Users are not objects — nothing to create.
  • Bindings are immutable in roleRef — pointing a binding at a different Role means delete and recreate.
  • RBAC is additive only. There is no deny rule; you cannot subtract a permission granted elsewhere.

Make a Pod use a ServiceAccount

k run api -n finance --image nginx:1-alpine --dry-run=client -o yaml > p.yaml
# hand-add under spec:, sibling of containers:
  serviceAccountName: auditor
k apply -f p.yaml
k get po api -n finance -o yaml | grep -i serviceaccount    # verify it landed
  • k run has no flag for it — generate, then hand-add the one line. (k set serviceaccount deploy/web auditor -n finance works for a Deployment.)
  • A live Pod's SA is immutable — delete and re-apply, same as env.
  • Token auto-mounted at /var/run/secrets/kubernetes.io/serviceaccount/ — three files: token, ca.crt, namespace.
  • Denied at runtime? k auth can-i list secrets --as=system:serviceaccount:finance:auditor -n finance separates an RBAC denial from everything else.

Normal user via CSR — key → cert → kubeconfig → RBAC

Users are not objects. Identity comes from a signed client certificate: CN becomes the username, O becomes the group.

# 1. key + CSR — usually already on disk, given by the task
openssl genrsa -out /root/dev-user.key 2048
openssl req -new -key /root/dev-user.key -out /root/dev-user.csr -subj "/CN=dev-user/O=developers"

# 2. base64 the request — -w0 or the wrapped output is invalid
cat /root/dev-user.csr | base64 -w0
apiVersion: certificates.k8s.io/v1
kind: CertificateSigningRequest
metadata:
  name: dev-user-csr
spec:
  request: <base64, ONE line>
  signerName: kubernetes.io/kube-apiserver-client
  usages:
  - client auth                   # space, list item — not client-auth
# 3. approve, then EXTRACT — approving writes no file
k certificate approve dev-user-csr
k get csr dev-user-csr -o jsonpath='{.status.certificate}' | base64 -d > /root/dev-user.crt

# 4. kubeconfig identity
k config set-credentials dev-user --client-certificate=/root/dev-user.crt --client-key=/root/dev-user.key --embed-certs=true
k config set-context dev-user --cluster=<cluster> --user=dev-user --namespace=development

# 5. RBAC — one-liners, bind to --user not --serviceaccount
k create role pod-reader -n development --verb=get,list,watch --resource=pods
k create rolebinding dev-user-pod-reader -n development --role=pod-reader --user=dev-user
k --context dev-user auth whoami            # CN=username, O=group, one line
k --context dev-user get pods               # allowed
k --context dev-user delete pod web         # must be Forbidden
  • The private key never leaves the machine — the CSR and the issued cert are both public.
  • set-context without --namespace lands the user in default; the Forbidden error then names the wrong namespace and reads as an RBAC bug.
  • delete --all against zero objects returns “No resources found”, never Forbidden — create a target before testing a deny.
  • expirationSeconds has no API default; omitted = the signer’s --cluster-signing-duration (1y). Read it back with openssl x509 -noout -dates.
  • CSRs are cluster-scoped — deleting the namespace leaves them behind.
  • --role takes the ROLE's name, --user / --serviceaccount takes the SUBJECT's name. Different nouns — don't collapse them. A binding made with --role=<username> and no subject flag points at a Role that doesn't exist and binds nobody.
  • Run BOTH probes: auth can-i <allowed> --as=U must say yes AND auth can-i <denied> --as=U must say no. A binding that grants nothing answers no to everything and reads as correct scoping.

  • YAML form → k8s.io search "Role and RoleBinding", Ctrl+F apiGroups:.
  • CSR flow → k8s.io search "Certificate Signing Requests" → section Normal user.

Native sidecar (post-2025 addition)

Since 1.29 (GA 1.33) the correct sidecar is an initContainers entry with restartPolicy: Always — not a second entry under containers:.

    spec:
      containers:
      - name: app
        image: nginx:1.25
        volumeMounts:
        - name: logs
          mountPath: /var/log/nginx
      initContainers:              # the sidecar lives HERE
      - name: logger
        image: busybox:1.28
        restartPolicy: Always      # <-- this is what makes it a sidecar
        command: ["sh","-c","tail -F /var/log/nginx/access.log"]
        volumeMounts:
        - name: logs
          mountPath: /var/log/nginx
      volumes:
      - name: logs
        emptyDir: {}
ShapeBehaviour
initContainers, no restartPolicyruns to completion, then the main containers start
initContainers + restartPolicy: Alwaysnative sidecar — starts first, keeps running, app waits for it
second entry under containers:plain sidecar — no ordering guarantee, cannot gate the app
  • restartPolicy on an individual container is only legal under initContainers.
  • Verify by phase: native → 2/2 Running. A non-native tail -F init container never exits and wedges at Init:0/1.
  • On a Job, a native sidecar exits after the app so the Job completes; a plain sidecar hangs it forever.
  • The volume name must match in three places: the volume definition and both volumeMounts.
  • Read its logs with k logs deploy/NAME -c logger.

  rules:
  - backendRefs:                  # catch-all, no matches:
    - name: web-svc
      port: 80
  - matches:                      # SECOND rule = its own dash
    - path:
        type: PathPrefix
        value: /api
    backendRefs:
    - name: api-svc
      port: 8080
  • Each - under rules: is ONE rule with its own matches + backendRefs.
  • Adding a backendRef to an existing rule's list = load-balancing between backends, not a new path route.

Match on a header — AND vs OR

  rules:
  - matches:
    - path:                     # `- path:` OPENS the match item
        type: PathPrefix
        value: /checkout
      headers:                  # sibling of path:, same item = AND
      - name: x-channel
        value: beta
    backendRefs:
    - name: beta-svc
      port: 80
Dash positionMeaning
new dash under rules:a separate routing decision
new dash under matches:an alternative way to match — OR
headers: beside path:, one itemboth must hold — AND
new dash under headers:another header that must ALSO match — AND
  • headers: matches on a header. filters: RequestHeaderModifier adds one. Different jobs — swapping them routes everyone to the wrong backend with no error.
  • Header match defaults to type: Exact (other value: RegularExpression).
  • hostnames: takes DNS names only (shop.example.com) — never a header, never the route name.
  • Most specific match wins regardless of file order (path length, then header count).
  • Never hand-align a second list item — yank the first (7yy, G, p) and edit the copy. :set ts=2 sw=2 et first.

Restrict which namespaces may attach routes

  listeners:
    - name: http
      protocol: HTTP
      port: 80
      allowedRoutes:
        namespaces:
          from: Same              # Same | All | Selector

Verify (the grade — conditions, not just created)

k get gateway web-gw -n store                  # PROGRAMMED True (+ADDRESS only if LB exists)
k describe gateway web-gw -n store             # listener: Attached Routes: 1
k describe httproute store-route -n store | grep -B2 -A8 Conditions
# want: Accepted True + "references resolved"
  • Attached Routes: 1 on the listener is the proof parentRefs actually bound. A route can read Accepted: True from its own controller and still be ignored by the Gateway.
  • Conflicted: Status: False is HEALTHY — negative-polarity condition, False = no conflict. Don't "fix" it.

Linux shell — the in-terminal toolkit

None of this is on kubernetes.io, and none of it needs the browser. On a laggy PSI desktop these beat a docs trip every time. man <cmd> and <cmd> --help are the only sources you get.

find — you know the name, not the path

find / -name 'kube-scheduler.yaml' 2>/dev/null      # exact name, whole disk
find /etc -name '*.conf' 2>/dev/null                # glob — QUOTE it
find / -name '*kubelet*' -type f 2>/dev/null        # files only, substring match
find /var/log -mmin -10                             # modified in the last 10 minutes
find / -name kubeadm -type f 2>/dev/null            # is the binary even on this host?

2>/dev/null on every whole-disk search — without it the permission-denied noise scrolls your hit off the screen. -name is case-sensitive, -iname is not. Quote the glob or the shell expands it before find ever sees it.

grep — reading config and logs

grep -r 'image:' /etc/kubernetes/manifests/    # -r recurse a whole directory
grep -n 'server:' /etc/kubernetes/kubelet.conf # -n line numbers
grep -A3 -B1 service values.yaml               # context After / Before
grep -i error /var/log/syslog                  # case-insensitive
grep -v '^#' /etc/default/kubelet              # -v INVERT — hide the comments
grep -c Running                                # -c count, do not print
grep -E 'Pending|Failed'                       # -E for alternation

-A3 is the flag that pays: nested YAML (helm show values, a manifest, a values file) only makes sense with the lines under the match.

systemctl / journalctl — the node ladder

systemctl status kubelet          # active? failed? last log lines for free
systemctl restart kubelet
systemctl enable --now kubelet    # start AND survive reboot — say BOTH
systemctl is-active kubelet
systemctl cat kubelet             # unit file + drop-ins, no path hunting
journalctl -u kubelet -f          # follow live
journalctl -u kubelet --since '10 min ago'
journalctl -u kubelet -p err      # errors only
journalctl -xeu kubelet           # last entries, with explanations

active is not healthy. A kubelet holding a bad kubelet.conf runs perfectly happily while the node reads NotReady. Go to journalctl before you believe status.

Secrets & ConfigMaps — create, then consume three ways

Every question is the same two halves: build the object, then wire it into a Pod as one env var, all env vars, or a volume. The wiring is where the points go.

Create

k create secret generic db-creds -n NS \
  --from-literal=username=appuser --from-literal=password=S3cr3tP4ss
k create secret generic db-creds --from-file=./ca.crt        # key = the FILENAME
k create secret generic db-creds --from-env-file=./app.env   # key=value per line
k create secret tls web-tls --cert=tls.crt --key=tls.key
k create secret docker-registry regcred --docker-server=S --docker-username=U --docker-password=P
k create configmap app-cfg -n NS --from-literal=LOG_LEVEL=debug
k create configmap app-cfg --from-file=./nginx.conf

--from-literal base64-encodes for you. Hand-written YAML under data: must already be base64 — or use stringData: and let the API server encode it.

Read a value back

k get secret db-creds -o jsonpath='{.data.password}' | base64 -d ; echo
k get cm app-cfg -o yaml

Consume — ONE key as an env var

    env:
    - name: DB_USER
      valueFrom:
        secretKeyRef:        # configMapKeyRef for a ConfigMap
          name: db-creds     # WHICH object
          key: username      # WHICH key inside it

key on its own is invalid. The ref always needs both halves — the object name and the key.

Consume — ALL keys as env vars

    envFrom:
    - secretRef:
        name: db-creds       # configMapRef for a ConfigMap

Consume — as a volume

  volumes:
  - name: creds
    secret:
      secretName: db-creds   # SECRET says secretName
      defaultMode: 0400      # optional
#   configMap:
#     name: app-cfg          # CONFIGMAP says name

    volumeMounts:
    - name: creds
      mountPath: /etc/db-creds
      readOnly: true
#     subPath: password      # mount ONE key as a single file

The volume names the object and nothing else. mountPath and readOnly belong to the volumeMount. Each key lands as a file named after the key, with the value as its contents.

FieldSecretConfigMap
single key as envsecretKeyRefconfigMapKeyRef
all keys as envsecretRefconfigMapRef
volume sourcesecret.secretNameconfigMap.name

That last row is the asymmetry that bites. A Secret volume says secretName; a ConfigMap volume says name. Nothing else in the API works this way.

Gotchas

  • Change the object: volume mounts refresh (~60s), env vars never → k rollout restart deploy X.
  • subPath mounts freeze — no refresh at all, ever.
  • optional: true lets the Pod start when the object is missing; without it you get CreateContainerConfigError.
  • immutable: true blocks every edit — delete and recreate.
  • Wrong namespace = the Pod never starts. The Secret must live in the Pod's namespace.

Docs keys

YAML layers — where every field actually lives

The most expensive mistake shape there is: a Pod field written at Deployment level. apply rejects it as strict decoding error: unknown field "spec.containers" — and that message names the exact layer you got wrong, so read it before re-reading your file.

One example, every layer

apiVersion: apps/v1
kind: Deployment
metadata:                                # the DEPLOYMENT's own identity
  name: web
  namespace: prod
  labels:
    app: web
spec:                                    # ---- DEPLOYMENT spec ----
  replicas: 3
  selector:
    matchLabels:
      app: web                           # MUST equal template.metadata.labels
  strategy:
    type: RollingUpdate
  template:                              # ---- POD TEMPLATE ----
    metadata:
      labels:
        app: web                         # what the selector matches
    spec:                                # ---- POD spec: everything about the Pod ----
      priorityClassName: high-priority
      serviceAccountName: deployer
      nodeSelector:
        hardware: gpu
      tolerations:
      - key: dedicated
        operator: Equal
        value: analytics
        effect: NoSchedule
      volumes:
      - name: shared
        emptyDir: {}
      initContainers:
      - name: log-ship
        image: busybox:1.28
        restartPolicy: Always            # native sidecar
      containers:                        # ---- CONTAINER list ----
      - name: nginx
        image: nginx:1.27
        command: ["/bin/sh", "-c", "sleep 3600"]
        ports:
        - containerPort: 80
        env:
        - name: ROLE
          value: producer
        envFrom:
        - configMapRef:
            name: site-config
        resources:
          requests:
            memory: "128Mi"
            cpu: "100m"
          limits:
            memory: "256Mi"
        volumeMounts:
        - name: shared
          mountPath: /data

Which layer owns what

LayerOwns
spec (Deployment)replicas, selector, strategy, template — and nothing else
spec.template.metadataPod labels + annotations
spec.template.specnodeSelector, nodeName, tolerations, affinity, priorityClassName, serviceAccountName, restartPolicy, volumes, initContainers, containers, hostNetwork, dnsPolicy
containers[]name, image, command, args, env, envFrom, ports, resources, volumeMounts, securityContext, probes

The rule that resolves every case: if it describes the POD, it goes under template.spec. If it describes ONE container, it goes in that container's entry.

Bare Pod vs Deployment — the two-level shift

A bare Pod has no template: its spec: is the Pod spec, so containers: sits at spec.containers — two levels shallower than the same field in a Deployment. Converting one manifest into the other is exactly where the layer gets lost.

The same template.spec shape covers StatefulSet, DaemonSet and Job. CronJob is one level deeper again: spec.jobTemplate.spec.template.spec.

Copying YAML out of the docs — the traps

  • Placeholders stay behind. Docs examples ship with their own names, images, ports and paths. After pasting, re-read the task and replace EVERY noun. A block that applies cleanly with the docs’ values is still a wrong answer.
  • Leftover keys from the example. Pasting over your own block can leave two command: or two env: keys. YAML takes the LAST one silently. Delete what you replaced.
  • Snippets are fragments. A docs snippet usually starts mid-object — check you carried its PARENT keys, and that its indentation matches your file’s level rather than the page’s.
  • Paste mangles indentation. In vim, :set paste before and :set nopaste after; without it autoindent staircases every line.
  • kubectl apply is the reviewer. Apply first and read the error — it names line, column and field path. Do not eyeball a manifest hunting for a typo.
  • Immutable fields. selector and most of a Pod’s spec cannot change in place: delete then apply. The error says field is immutable and re-applying will never fix it.

Reading a docs page fast

  • Land on the page, then Ctrl+F the FIELD NAME, not the concept — tolerations, volumeClaimTemplates, secretName. The YAML example containing it is what you want, and it is usually one screen below the heading.
  • Most pages put a complete, runnable manifest near the top. Take that whole block rather than assembling fragments.
  • If a field is not in the page’s example it is probably not exam-scope — check kubectl explain <kind>.spec.<field> before hunting further.
