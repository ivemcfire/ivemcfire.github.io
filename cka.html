Paste, don't type (kills exact-name fails)

Never transcribe a string the grader checks. Select it and paste it.
  • Paste the nouns: resource names, namespaces, image tags, ports, paths — straight from the question text (it's selectable). No typo = no silent zero.
  • Paste docs YAML skeletons, then paste the question's names into them.
  • Always paste: base64 secrets, tokens, join commands, long flags.
  • Type the verbs: short imperative commands (k get, k create, k describe) — faster typed, and a typo just errors instead of silently failing.

Maps to memorize-vs-lookup: verbs typed, nouns pasted. Terminal paste = Ctrl+Shift+V.

Don't let a pasted command auto-run

Docs "copy" buttons and triple-click grab the trailing newline — that newline is Enter, so a pasted command fires before you can read it.
  • Single-line command: type # first, then paste. The whole line is commented — it prints, doesn't run. Read it, up-arrow, strip the #, run. (# beats echo: no $/quote/backtick expansion.)
  • Multi-line / YAML: # only protects the first line. Paste into the editor instead (vim :set paste first).

The post-2025 remote-desktop CKA is terminal + vim/nano + a Firefox docs window. No VS Code, no code-server, no IDE. Don't plan around one.

Mechanical checklist — the leaks that cost points when the knowledge was fine

Built from a 17-question simulator sit where not one point was lost to a concept. Every loss was mechanical. Run this list, not more theory.

After you write anything

  • cat the file. Always. A file that exists and a file that is correct are different things.
  • Answer files get bare values — no Name: labels carried over from describe, no JSON quotes or trailing commas from inspect.
  • cat -A on every file answer. It exposes trailing padding spaces that plain cat cannot show. Strip them with :%s/ *$//.
  • Container logs usually go to STDERR (httpd, nginx, most JVM apps). A bare > writes an empty file — use 2>&1 after the >.

After you edit anything

k get rs -n NS                    # new ReplicaSet = the template change landed
k get cm NAME -o yaml | grep X    # ConfigMap edits
  • k edit can silently not save. Verify at the object: new ReplicaSet? generation bumped? Does the READY column show the right container count?
  • get -o yaml is a SNAPSHOT, not a manifest. Before re-applying strip resourceVersion (this one actively breaks — Conflict: object has been modified), uid, creationTimestamp, generation, status:.
  • apply MERGES maps, it does not replace them. Deleting a key from your YAML does not delete it from the cluster. Escape hatch: k replace --force -f, or delete then apply.
  • spec.selector on a Deployment is immutable — no edit path, only delete + recreate. Get it right before the first apply.
  • apply printing unchanged after you edited the file means the edit never reached the object. Same family as generation: 1 after a k edit — the tool told you it did nothing.
  • Duplicate YAML keys do not error — the last one silently wins. Edit the existing block; never append a second selector: / ports:.

Before you diagnose

  • k get <kind> first. A missing object and a selector that matches nothing look identical from the client side.
  • Pending pod with a volume → read the PVC object before re-reading the Deployment.
  • k get po -o wide is the single source of truth for placement. Read the node name, never recall it.

Location

ssh <node> sudo crictl logs <id> > /course/X/file 2>&1   # redirect runs HERE, not there
  • The question names a host → ssh <host> is the first command; hostname proves it landed.
  • Worker hostnames resolve only from their controlplane: base terminal → ssh <cp> → ssh <cp>-node1.
  • Answer-file directories live on the controlplane, not the worker.
  • kubectl does not work from a worker (no admin kubeconfig). SSH only for node-local files / systemctl / crictl.
  • crictl talks to the runtime socket directly → always needs sudo. That's also why it still works when the API server is down.

Values

Docs give STRUCTURE. The cluster gives VALUES. Never type a value you could read off an object.

  • Never add a field the task didn't ask for — hostnames:, storageClassName: manual, an extra listener. Unrequested values can only cost.

Fatal mistakes — ranked by how often they cost the exam

These are scoring failures, not knowledge failures. Grade every practice question against this list, not just against "did it work".
  1. Over-running one question. Past 15 minutes: flag it and move. The most repeated failure story is running out of time before returning to flagged questions. Budget ~7 min/question, two-pass, bank the cheap ones first.
  2. Wrong namespace / wrong context / wrong node. A correct answer in the wrong place scores zero. k config use-context <name> is the first action of every question; explicit -n on every graded command.
  3. Not verifying before moving on. Exercise the object, don't re-read it. Endpoints populated ≠ something listening. auth can-i --as matches a username string, not an existing ServiceAccount.
  4. Static pod edited with kubectl. It is a FILE in /etc/kubernetes/manifests/ on the control plane. Never k delete, never k edit.
  5. ConfigMap changed without a restart. env / envFrom / subPath mounts → k rollout restart deploy <name> -n <ns>. A plain volume mount self-syncs.
  6. -f reflex on a Kustomize task. A kustomization directory needs -k.
  7. No backup before editing something critical. k get X -o yaml > backup.yaml — five seconds.

Two personal additions

  • When a question names a host, do the whole question from that host — diagnosis, fix, and proof. Verifying from somewhere else is how a working fix gets graded as a miss.
  • Strip what the task didn't ask for. Docs examples carry extra fields; they come along for the ride and can only cost.

Output & writing answers to files

When a task says “use kubectl only” — no grep, awk or cut — and wants values written to files, custom-columns and jsonpath are the only tools that do this.

Cheapest first — climb only when the rung below can't do it

NeedReach forCost
one value, one objectk get node NAME -o wide → read it off the screen0 special chars
one field per object, many objects-o custom-columns=H:.the.path --no-headersone dotted path
field inside a list, position varies-o jsonpath='{.status.addresses[?(@.type=="InternalIP")].address}'quote nesting

Gamble worth taking: on kubeadm nodes .status.addresses[0] is the InternalIP ([1] is Hostname). Use [0], confirm against -o wide, move on.

  • A wrong path never errors — it prints <none>. Check the values, not the layout. .spec.container[0] (singular) is the classic; it's containers.
  • --no-headers needs no =true.
  • jsonpath emits no trailing newline — cat runs into the prompt. Harmless to a grader.
  • Filter syntax: [?(@.type=="InternalIP")] — @ is the current item; inner quotes must be double inside a single-quoted shell string.

Gotchas

  • --no-headers omitted → the literal word NAME becomes line 1 of your answer.
  • -o name gives pod/web, not web.
  • jsonpath has no substring filter — filter by namespace or label, never by name fragment.
  • .items[*] only exists on a LIST; a single object is addressed directly.
  • Single-quote the jsonpath — the shell eats {} and *.
  • cat -A the file before moving on — trailing spaces are invisible to plain cat and score zero.

Workloads — create / inspect / modify

HPA + ResourceQuota

The hard version of this task: an HPA that scales to 3 pods, where the memory requests must be cut so 3 pods fit under a quota. With a quota of 1100Mi and pods requesting 600Mi, three of them need 350Mi each.

k autoscale deploy web -n NS --min 1 --max 3 --cpu-percent 50
k describe quota -n NS                          # Used vs Hard — the discovery step
k set resources deploy web -n NS --requests=memory=350Mi

Budget ÷ replicas, round down, leave headroom: 1100 ÷ 3 = 366 → use 350. Write YAML only if the task names behavior, stabilization windows, or a non-CPU metric.

  • A quota counts requests, not limits. The scheduler reads requests too; limits only bite at runtime (OOMKill).
  • A quota on requests.memory makes a memory request mandatory — a Pod without one is rejected.
  • Over quota surfaces on the ReplicaSet, not the Pod: k describe rs -n NS → exceeded quota. There's no Pending Pod to inspect.
  • cpu: <unknown>/50% = no metrics-server. The object is still correct and still grades.
  • The HPA needs a CPU request — utilization is a percentage of the request. No request, no denominator, no scaling.
  • HPA changes the replica count; VPA changes per-pod requests and is not on the exam.

Gotchas

  • run = pod, no resource noun (docker run legacy). k run pod catalog → pod NAMED pod, catalog becomes the container command → CrashLoop. create needs the noun; run never does.
  • expose --target-port only when the container port actually differs. Endpoints populate as podIP:targetPort with NO listener check — wrong value = populated-but-dead service. Read the PORT in k get endpoints, not just presence.
  • Container name = image basename AT CREATE TIME (incl. typos: --image=ngnix → container ngnix). It's the CONTAINER token for set image. Don't assume it — look it up: k describe deploy/NAME | grep -i image.
  • k set image deployment/NAME container=image uses =, not space.
  • k rollout status blocks until rollout completes (or stalls). If it hangs, image is failing — check describe pod.
  • k scale changes replica count immediately; no rollout, no new revision.
  • k delete deployment cascades to ReplicaSet + pods automatically. k delete pod on a deployment-owned pod just re-creates it.
  • describe deploy renders MinReadySeconds and 0 max unavailable, 1 max surge — but NOT revisionHistoryLimit / progressDeadlineSeconds. Verify those with k get deploy X -o yaml | grep -E 'revisionHistoryLimit|progressDeadlineSeconds'.
  • An edit that looks applied may not have landed. Always re-read the field you just set.

Toleration only permits, never attracts — a tolerating pod may still land elsewhere. "Only this pod, only on this node" = taint the node (repel others) + nodeSelector (pull this pod). One alone isn't enough.

Taints (imperative)

k taint nodes node01 spray=mortein:NoSchedule        # key=value:effect
k describe node node01 | grep -i taint               # check

Control-plane ships with node-role.kubernetes.io/control-plane:NoSchedule — that's why workloads avoid it.

Toleration / nodeSelector (pod YAML, under spec:)

  tolerations:               # spec level - sibling of containers:
  - key: "spray"
    operator: "Equal"        # Equal -> value: required
    value: "mortein"         # Exists -> DELETE this line
    effect: "NoSchedule"
  nodeSelector:
    size: Large              # exact equality ONLY (no OR/NotIn)

nodeName — pin to one node, one line (under spec:)

  nodeName: cluster4-node01
  • Skips the scheduler entirely; that node's kubelet takes the pod. Use it when the task just says "on node X".
  • Wrong or nonexistent name → Pending forever with NO event (the scheduler never ran). nodeSelector/affinity give you FailedScheduling instead.
  • Ignores taints, affinity and resource fit.

Node affinity (when nodeSelector can't — OR / NotIn / Exists)

  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:   # hard; preferred... = soft
        nodeSelectorTerms:
        - matchExpressions:
          - { key: size, operator: In, values: [Large, Medium] }

Operators: In · NotIn · Exists · DoesNotExist · Gt · Lt.

Gotchas

  • Pin to a node by NAME → key kubernetes.io/hostname. node-role.kubernetes.io/* labels have EMPTY values — they can never match a node name.
  • Read identifiers off the object, never from memory: k get nodes for names, k get node X --show-labels for keys.
  • Affinity needs all three levels: nodeAffinity: → requiredDuringSchedulingIgnoredDuringExecution: → nodeSelectorTerms:. Skipping the middle one = rejected.
  • Affinity is a POD property — in a Deployment it goes at template.spec.affinity (6sp, sibling of containers:).
  • operator: Exists → NO value: line (matches any value); operator: Equal → value: required. Both together = the Pod is rejected: value must be empty when operator is Exists.
  • Toleration value is string-exact — a typo (mortain ≠ mortein) leaves the pod Pending: the "but I added a toleration!" trap. Paste the noun.
  • No matching node (nodeSelector / required affinity) = pod Pending forever.
  • Pending diagnosis: k describe po X → Events → "untolerated taint" / "didn't match node selector".
  • comma = AND in selectors; get all excludes cm/secret/pvc/ingress/netpol.

Gotchas

  • -- is not optional. Forgetting it = "unknown flag" error.

Ingress — create

The generator does the whole job — hand-writing the YAML is rarely worth it.

k create ingress NAME -n NS --rule="host/path=SVC:PORT"

--rule = host/path=service:port[,tls[=secret]] · trailing * on the path = pathType: Prefix · no * = Exact.

The comma slot is TLS, never a second path. Two paths = repeat the whole --rule flag. Keep it on one line — a \ followed by a space is not a continuation.

spec:
  ingressClassName: nginx

Triage — "A can't reach B, N policies exist, fix the right one"

Egress — the DNS trap

Any egress policy selecting a Pod kills its DNS unless you re-allow port 53. The symptom misleads: name resolution dies, so every destination looks blocked — including the one you just permitted.

  egress:
  - to:                                  # the destination you want
    - podSelector:
        matchLabels:
          app: backend
    ports:
    - protocol: TCP
      port: 80
  - to:                                  # + DNS, or nothing resolves
    - namespaceSelector:
        matchLabels:
          kubernetes.io/metadata.name: kube-system
    ports:
    - protocol: UDP
      port: 53
    - protocol: TCP
      port: 53
  • Shorter DNS allow: omit to: and give only ports: — that port, any destination.
  • Probe by IP as well as by name. Name fails while IP works = the DNS symptom.
  • kubernetes.io/metadata.name is not on the NetworkPolicy docs page — its examples use hand-made labels. Use k get ns --show-labels; the docs home for it is Well-Known Labels, Annotations and Taints.

The model (the whole game)

SlotMeans
spec.podSelector (top)WHO you protect — the destination. {} = all pods in ns.
ingress.from[].podSelectorWHO is allowed in — the source.

Read the task — "traffic TO x FROM y" — straight into the two slots. The two selectors are different pods: read each one's real label off the question, don't autopilot app:. A wrong key on the top selector matches nothing → the policy applies to no pod → silent allow-all. policyTypes listed with no matching rules = deny-all that direction (Egress alone cuts DNS).

Allow ingress pod → pod (the 90% case)

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: allow-web-to-db, namespace: prod }
spec:
  podSelector:
    matchLabels: { app: db }       # protected (TO)
  policyTypes: [Ingress]
  ingress:
  - from:
    - podSelector:
        matchLabels: { app: web }  # allowed (FROM)
    ports:                         # optional; omit = all ports
    - { protocol: TCP, port: 80 }

Variants — swap the from block

  • From a namespace: - namespaceSelector: {matchLabels: {kubernetes.io/metadata.name: dev}}
  • ns AND pod: both selectors in one - item · ns OR pod: two separate - items.
  • Deny-all ingress: podSelector: {} + policyTypes: [Ingress] + no ingress rules.
  • Egress: policyTypes: [Egress] + egress: [{to: [...], ports: [...]}].

Verify both directions (always) — busybox:1.28

# destination IP
k get pod DST -n ns -o wide
# allowed: prober carries the trusted LABEL -> serves the page
k run t --image=busybox:1.28 --labels=<allowed-label> -n ns --rm -it --restart=Never -- wget -qO- --timeout=2 <ip>:80
# blocked: no label -> blocked (policy working)
k run t --image=busybox:1.28 -n ns --rm -it --restart=Never -- wget -qO- --timeout=2 <ip>:80

Policy trusts the label, not the pod name/image — the allowed prober just needs the right label. It also needs a working tool: nginx has no wget, so use busybox, and pin :1.28 (latest's wget returns a false connection refused).

Gotchas

  • Separate - = OR; two selectors in one - = AND. Trips everyone.
  • Cross-ns allow test: the prober must ALSO run in the allowed namespace — right label + wrong ns = deny path. Check pod <ns>/<name> in the probe output.
  • Always prove the deny — an OR-bug policy and a dead CNI look IDENTICAL from the allowed side (both succeed). Only the blocked probe distinguishes them.
  • Source ns must carry a label to match — built-in kubernetes.io/metadata.name.
  • CNI without policy support (flannel) = policy silently no-ops.
  • Deny shows as timeout OR connection refused depending on the CNI (drop vs reject). Don't read allow/deny off the error string — judge by the controlled comparison: labeled pod gets in, unlabeled is blocked.
  • Running ≠ serving: a -- sleep override leaves the pod Running but its port closed (→ refused). Verify the target with a probe, not the status phase.
  • Wrong namespace = 0 points. Set it before anything else.

  • Fix the minimum that makes it work, then stop. An extra "improvement" on a graded object can fail a spec diff even when traffic flows.
  • Read state before mutating. If the task says the object exists, k get it — don't recreate it.
  • Verify on the cluster/node you fixed. Node names in any output are the free context check.
  • Don't invent faults in fields you haven't verified — status first, files second.

RBAC — ServiceAccount → Role → Binding

The chain (4 nouns, always this order)

SA → Role → RoleBinding → verify = who → what they can do → glue → prove. Memorize the shape; look up the flags with --help.

Namespaced (Role + RoleBinding) — -n on ALL THREE creates

k create sa auditor -n finance
k create role pod-reader -n finance --verb=get,list,watch --resource=pods
k create rolebinding auditor-bind -n finance --role=pod-reader \
     --serviceaccount=finance:auditor   # ns:name

Verify (impersonate the SA)

k auth can-i list   pods --as=system:serviceaccount:finance:auditor -n finance  # yes
k auth can-i delete pods --as=system:serviceaccount:finance:auditor -n finance  # no

Cluster-wide (ClusterRole + ClusterRoleBinding) — NO -n

k create clusterrole node-reader --verb=get,list,watch --resource=nodes
k create clusterrolebinding node-read --clusterrole=node-reader \
     --serviceaccount=finance:auditor

The two SA syntaxes (the slip)

WhereFormat
--serviceaccount=finance:auditor (ns:name)
--as=system:serviceaccount:finance:auditor (full prefix)

Gotchas

  • Bind the role you made, not built-in admin (admin = broad, breaks least-privilege).
  • --serviceaccount= with no namespace → defaults to default:auditor → binds nothing.
  • All three namespaced creates need -n — silent zero otherwise.
  • Multiple verbs/resources = comma list, no spaces: --verb=get,list,watch.
  • Bind to a user/group instead of an SA: --user=jane / --group=devs.

Make a Pod use a ServiceAccount

k -n NS run api --image nginx:1-alpine --dry-run=client -o yaml > p.yaml
# hand-add under spec:, sibling of containers:
  serviceAccountName: secret-reader
  • k run has no flag for it — generate, then hand-add the one line.
  • Token auto-mounted at /var/run/secrets/kubernetes.io/serviceaccount/ — three files: token, ca.crt, namespace.
  • Denied? k auth can-i list secrets --as system:serviceaccount:NS:SA separates an RBAC denial from everything else.

Helm — package manager (post-2025 addition)

helm.sh/docs is now an allowed exam tab. Lookup-class — know the ~8 commands + the values flow.

Repo URL + local path + pinned version

Why a task gives you both a URL and a path: you pull from one and install from the other. --version works on a repo reference (bitnami/nginx); a local path ignores it, because a local chart's version lives in its Chart.yaml. --untardir lands the chart at <dir>/<chartname>/, so the install path ends with the chart name.

helm search repo <chart> --versions | head -3 is only worth the keystrokes when a pinned version errors as not found.

A path in the question? ls IT BEFORE CHOOSING FLAGS. “Deploy from the repository” plus a path does not mean pull:

helm list shows less than you think

helm list -A          # every namespace — DEPLOYED only

helm status REL -n NS
k get secret -A | grep sh.helm.release   # helm's own records

An empty helm list -A means “no HEALTHY release”, not “no release”. -A = all namespaces; -a = all states. Different flags. Helm also reads your current kubeconfig context — wrong cluster reports nothing.

install vs upgrade — read the task wording

  • install = NEW release, fails if the name exists. upgrade = same release, revision +1, keeps history.
  • Release NAME is your handle; CHART is the package. One chart → many releases.
  • A chart can be a path: helm install my-rel /root/new-version (dir with Chart.yaml + values.yaml + templates/).
  • helm lint <chart> is the "validate" verb; helm install --dry-run also validates.
  • Proof of which version is live: helm list → CHART (name-0.1.1) + APP VERSION.

Which values? two different questions

helm show values <repo/chart>          # the CHART'S DEFAULTS
helm show values <chart> | grep -i replica
helm get values <release> -n <ns>      # YOUR RELEASE'S OVERRIDES (-a = merged with defaults)
helm get metadata <release> -n <ns>    # chart name + VERSION + revision of a live release
k get po,svc -n <ns>                   # what is ACTUALLY running
  • show values prints the chart's entire values.yaml with its defaults — not a subset. Redirect it to a file (> defaults.yaml) when the task asks for one; your own override file repeats only the lines you change.
  • An override file is nested YAML (service: then two spaces, type: NodePort). Dotted service.type is --set syntax only — in a file it silently becomes a key nobody reads.
  • Chart values (replicaCount, service.type) are defined by the chart. They are not helm flags — they never appear in helm --help or on helm.sh/docs.
  • helm get values is a false-green on its own: it reports what you asked for, not what is running.

Native sidecar (post-2025 addition)

Since 1.29 (GA 1.33) the correct sidecar is an initContainers entry with restartPolicy: Always — not a second entry under containers:.

    spec:
      containers:
      - name: app
        image: nginx:1.25
        volumeMounts:
        - name: logs
          mountPath: /var/log/nginx
      initContainers:              # the sidecar lives HERE
      - name: logger
        image: busybox:1.28
        restartPolicy: Always      # <-- this is what makes it a sidecar
        command: ["sh","-c","tail -F /var/log/nginx/access.log"]
        volumeMounts:
        - name: logs
          mountPath: /var/log/nginx
      volumes:
      - name: logs
        emptyDir: {}
ShapeBehaviour
initContainers, no restartPolicyruns to completion, then the main containers start
initContainers + restartPolicy: Alwaysnative sidecar — starts first, keeps running, app waits for it
second entry under containers:plain sidecar — no ordering guarantee, cannot gate the app
  • restartPolicy on an individual container is only legal under initContainers.
  • Verify by phase: native → 2/2 Running. A non-native tail -F init container never exits and wedges at Init:0/1.
  • On a Job, a native sidecar exits after the app so the Job completes; a plain sidecar hangs it forever.
  • The volume name must match in three places: the volume definition and both volumeMounts.
  • Read its logs with k logs deploy/NAME -c logger.

Gateway API — Ingress successor (post-2025 addition)

apiGroup gateway.networking.k8s.io. Three layered objects.

The three objects

ObjectOwnerDoes

Gatewaycluster oplisteners: ports/protocols/hosts

Inspect

k get gatewayclass
k get gateway,httproute -A

Gateway + HTTPRoute (skeletons)

kind: Gateway
spec:
  gatewayClassName: <class>      # from k get gatewayclass
  listeners:
    - name: http
      protocol: HTTP
      port: 80
---
kind: HTTPRoute
spec:
  parentRefs:
    - name: web-gw                # the Gateway name
  rules:
    - matches:
        - path: { type: PathPrefix, value: / }
      backendRefs:
        - name: web-svc           # a Service, not a pod
          port: 80

Verify — read spec: BEFORE status:

k get gateway <n> -n <ns> -o yaml | grep -A15 '^spec:'     # what you asked for
k get gateway <n> -n <ns> -o yaml | grep -A20 '^status:'   # what the controller did
  • A green status: block can describe the spec you thought you replaced. Four True conditions prove nothing if the edit never landed.
  • No error out of k edit ≠ saved. Re-read spec:.

Multiple rules on one HTTPRoute

  rules:
  - backendRefs:                  # catch-all, no matches:
    - name: web-service
      port: 80
  - matches:                      # SECOND rule = its own dash
    - path:
        type: PathPrefix
        value: /api
    backendRefs:
    - name: api-service
      port: 8080
  • Each - under rules: is ONE rule with its own matches + backendRefs.
  • Adding a backendRef to an existing rule's list = load-balancing between backends, not a new path route.

Match on a header — AND vs OR

  rules:
  - matches:
    - path:                     # `- path:` OPENS the match item
        type: PathPrefix
        value: /checkout
      headers:                  # sibling of path:, same item = AND
      - name: x-channel
        value: beta
    backendRefs:
    - name: beta-svc
      port: 80
Dash positionMeaning
new dash under rules:a separate routing decision
new dash under matches:an alternative way to match — OR
headers: beside path:, one itemboth must hold — AND
new dash under headers:another header that must ALSO match — AND
  • headers: matches on a header. filters: RequestHeaderModifier adds one. Different jobs — swapping them routes everyone to the wrong backend with no error.
  • Header match defaults to type: Exact (other value: RegularExpression).
  • hostnames: takes DNS names only — never a header, never the route name.
  • Most specific match wins regardless of file order (path length, then header count).
  • Never hand-align a second list item — yank the first (7yy, G, p) and edit the copy. :set ts=2 sw=2 et first.

Restrict which namespaces may attach routes

  listeners:
    - name: web
      protocol: HTTP
      port: 80
      allowedRoutes:
        namespaces:
          from: Same              # Same | All | Selector

Verify (the grade — conditions, not just created)

k get gateway <name>                        # PROGRAMMED True (+ADDRESS only if LB exists)
k describe gateway <name> -n <ns>           # listener: Attached Routes: 1
k describe httproute <name> | grep -B2 -A8 Conditions
# want: Accepted True + "references resolved"
  • Attached Routes: 1 on the listener is the proof parentRefs actually bound. A route can read Accepted: True from its own controller and still be ignored by the Gateway.
  • Conflicted: Status: False is HEALTHY — negative-polarity condition, False = no conflict. Don't "fix" it.

Gotchas

  • HTTPRoute parentRefs.name MUST match the Gateway (+ns if cross-ns).
  • gatewayClassName must be a real class — check first.
  • backendRefs → a Service. Migration Q's compare vs single-object Ingress.
  • rules: is a LIST — deleting the matches: block must keep the dash: - backendRefs:.
  • Docs-noun sweep after paste: pass 1 = names (example-gateway!), pass 2 = class/path/port. Your own parentRefs tells you the Gateway's required name.
